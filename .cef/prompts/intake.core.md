# CEF — Intake Core

## PURPOSE

Convert an initial task request into a structured, reviewable task definition.

Intake is a planning, investigation and clarification procedure.

It does not authorize implementation.

## REQUIRED CONTEXT

Before starting:

1. Read `.cef/ENGINE.md`.
2. Read `.cef/WORKFLOW.md`.
3. Read `.cef/TASK_STATE.md`.
4. Inspect relevant repository files when necessary.

If a required file cannot be located or read, report the problem and stop the affected operation.

Do not assume that repository structure, dependencies, contracts or implementation details exist without evidence.

## INFORMATION PROVENANCE

Use the canonical provenance classifications defined in `.cef/ENGINE.md`.

Apply the most specific classification supported by the available evidence.

### CONFIRMED

Information explicitly established by the human or supported by sufficient and unambiguous evidence.

Use this classification for established requirements, constraints, decisions and facts that do not require a more specific provenance classification.

When confirmation comes from evidence rather than an explicit human statement, identify its source.

### VERIFIED IN REPOSITORY

Technical facts directly established through repository inspection or executed validation.

Use this classification when the evidence comes directly from repository files, commands or validation results.

Repository verification establishes technical facts, not automatically human intent or approval.

When relevant, distinguish a verified technical fact from a separately confirmed human requirement or decision.

### AI SUGGESTION

Recommendations, interpretations or proposed solutions generated by the AI and awaiting human approval.

These are not approved requirements or decisions.

### PENDING ANALYSIS

Information for which sufficient evidence is not currently available and further investigation is required.

### PENDING HUMAN DECISION

A decision, clarification or approval that requires an explicit human response.

### UNKNOWN

A value or fact that cannot currently be established from available evidence.

Do not silently convert UNKNOWN into an assumption.

### Classification Rules

- Use the most specific applicable classification.
- Do not classify repository evidence as human approval.
- Do not classify an AI suggestion as confirmed merely because it appears technically plausible.
- Preserve the source of evidence supporting every material conclusion.
- Record assumptions separately, including their source, uncertainty and potential impact.
- When evidence is insufficient, use PENDING ANALYSIS or UNKNOWN as appropriate.

## CONFLICT HANDLING

When relevant sources conflict:

1. Identify the conflicting statements.
2. Identify their respective sources.
3. Explain the practical impact.
4. Present the alternatives when they can be established.
5. Request a human decision.

Do not silently reconcile material conflicts.

Material conflicts affecting scope, contracts, acceptance criteria, severity or implementation must block the affected planning decision.

Independent investigation may continue only when it does not assume a resolution.

Follow the conflict handling rules in `.cef/ENGINE.md`.

## INTAKE PROCEDURE

### 1. Understand the request

Identify:

- Objective
- Expected outcome
- Acceptance criteria
- Explicit constraints
- Out-of-scope items

Distinguish the requested outcome from the proposed implementation.

Do not ask questions that can be answered by inspecting the repository.

### 2. Inspect relevant context

Inspect only files relevant to understanding the task.

Establish repository facts through direct evidence.

Distinguish verified facts from assumptions and AI suggestions.

Do not flood the context with unrelated repository files.

### 3. Identify uncertainties

Classify unresolved information using the canonical provenance categories.

Ask concise questions when human clarification is necessary.

Do not invent missing requirements or decisions.

Do not ask the human to provide information that can be reliably established through repository inspection.

### 4. Assess the task

Propose:

- Scope
- Severity
- Confidence
- Assumptions
- Risks
- Initial implementation direction
- Verification strategy

Follow the classification, severity and confidence rules in `.cef/ENGINE.md`.

Severity and confidence must be assessed independently.

Low confidence must be reported and must not be disguised by plausible assumptions.

If an approval gate is triggered, follow the exact human approval procedure defined in `.cef/ENGINE.md`.

Do not treat an initial implementation direction as an approved implementation plan.

### 5. Prepare the TASK_STATE draft

Prepare a complete proposed version of `.cef/TASK_STATE.md`.

At this stage, prepare the draft in memory.

Do not write to `.cef/TASK_STATE.md` yet.

The draft must:

- Preserve the provenance of requirements and decisions.
- Separate confirmed information from repository evidence.
- Identify AI suggestions awaiting approval.
- Record pending analysis and human decisions.
- Distinguish proposed actions from completed actions.
- Include the proposed scope, severity, confidence and verification strategy.
- Preserve the evidence supporting material conclusions.

Use an established project Task ID convention when one exists.

Do not invent a Task ID when its format or assignment is not established. Mark it as pending and request human clarification when necessary.

### 6. Present the proposed task definition

Present the complete TASK_STATE draft to the human for review.

Clearly identify:

- Confirmed requirements and facts
- Verified repository evidence
- AI suggestions
- Pending analysis
- Pending human decisions
- Unknown information
- Proposed scope
- Severity and confidence
- Assumptions
- Risks
- Initial implementation direction
- Verification strategy

Request one explicit authorization:

**Authorization to record TASK_STATE**

Obtain explicit approval before writing the proposed draft to `.cef/TASK_STATE.md`.

This authorization permits only the recording of the approved task definition.

It does not authorize:

- Implementation
- Application source changes
- Dependency installation
- Configuration changes
- Operations outside the approved task definition
- Destructive operations

Do not infer authorization from silence, ambiguous wording or previous approval for a materially different operation.

If the human requests changes, revise the draft and present it again before writing.

### 7. Record and verify TASK_STATE

Only after receiving explicit authorization to record the proposed task definition:

1. Write the approved content to `.cef/TASK_STATE.md`.
2. Read the resulting file.
3. Verify that its content matches the approved draft.
4. Report the result.

If the write or verification fails:

- Preserve the approved draft and available information.
- Report the failure.
- Do not claim that TASK_STATE was successfully recorded.
- Do not proceed to planning as though recording had succeeded.

### 8. Handoff to planning

After TASK_STATE has been successfully recorded and verified:

- Confirm that the task definition is available for planning.
- Preserve unresolved questions and risks.
- Identify any approval gates that may affect subsequent planning.
- Follow `.cef/WORKFLOW.md` and proceed to PHASE 1 — PLAN.

Implementation authorization belongs exclusively to PHASE 2 — REVIEW.

Intake must not request or grant implementation authorization.

## STRICT RESTRICTIONS

During Intake:

- Do not implement the task.
- Do not modify application source code.
- Do not install dependencies.
- Do not change application configuration.
- Do not execute destructive operations.
- Do not modify metrics or historical records.
- Do not modify unrelated documentation.
- Do not treat silence as approval.
- Do not write TASK_STATE before explicit authorization.
- Do not treat authorization to record TASK_STATE as authorization to implement.

The only permitted write operation during Intake is recording the approved task definition in `.cef/TASK_STATE.md`, followed by verification.

Any other write operation requires its own applicable authorization.

## COMPLETION

Intake is considered recorded successfully only when:

1. The objective and acceptance criteria are sufficiently clear.
2. Relevant uncertainties are classified.
3. Material conflicts are resolved or explicitly left pending.
4. Severity and confidence are proposed.
5. The complete TASK_STATE draft has been presented to the human.
6. Explicit authorization to record the task definition has been obtained.
7. TASK_STATE has been written and its content verified.

Implementation authorization is not part of Intake.

If the task definition is recorded successfully, report:

`Intake recorded — implementation not authorized.`

If authorization to record has not been obtained, Intake remains pending human decision.

## COMPLETION REPORT

Report:

- Objective
- Confirmed requirements and facts
- Verified repository evidence
- AI suggestions
- Pending analysis
- Pending human decisions
- Unknown information
- Scope
- Severity
- Confidence
- Assumptions
- Risks
- Initial implementation direction
- Verification strategy
- TASK_STATE recording status
- Implementation authorization status: NOT REQUESTED

Never claim implementation is authorized during Intake.
